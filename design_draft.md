## 1. What this is (one paragraph)

Bharat Streams is a **new Stremio-protocol addon, built fresh from scratch** with `stremio-addon-sdk` (Node.js). It does two jobs in one install: (a) **catalogs** — "New Indian Releases" first, then OTT Releases and per-language rows, powered by TMDB, with IMDb (`tt…`) ids so Cinemeta resolves detail pages; (b) **streams** — it asks three free source addons (Torrentio, Comet, HdHub) for streams, then parses, filters (Hindi/English only, 1080p max, never 4K, no CAM, no dead torrents), dedupes, sorts (Hindi-presence → resolution → seeders) and formats them minimally, so that **the first stream in the list is already the right one** (Hindi, 1080p, seeded) and Nuvio's "Auto-play first source" plays it with one click — deterministically when Nuvio's auto-play scope is restricted to Bharat Streams (§8, decision D8). No paid services, no debrid, no logins, no accounts. **v3 note:** revised after a live audit of basant's 10 installed Nuvio addons (18 Nov 2026, §15) — StreamRadar India already covers Indian OTT discovery (but gives no free streams), HdHub 1.0.7 is already installed and active, and SELection is already a tuned AIOStreams. This draft now says what Bharat Streams must still do differently.

## 4. Architecture

```
Nuvio (Windows desktop)
  │  manifest.json / catalog / stream  (HTTPS, Stremio protocol)
  ▼
Bharat Streams server (Node.js, stremio-addon-sdk)
  ├── Catalog handler  ──► reads prebuilt rows from persistent store
  │                          (Vercel Blob/KV, §6.3) — never calls TMDB
  │                          per request
  ├── Daily cron rebuild ──► TMDB API (discover + external_ids +
  │                          detail post-filter) ──► writes rows + id map
  │                          to the store (keeps yesterday's on failure)
  └── Stream handler (tt… ids ONLY) ──► parallel fan-out, 3 sources
        ├── Torrentio     GET /stream/{type}/{id}.json
        ├── Comet         GET /stream/{type}/{id}.json
        └── HdHub         GET /stream/{type}/{id}.json
      then: validate → parse (per-source) → filter → dedupe
            → sort → format → { streams: [...] } (cap 40)
```

- **One service, two resources in v1: `catalog` + `stream`.** No `meta` resource — detail pages come from Cinemeta via `tt…` ids (§6.4). No `subtitles` resource — subtitles stay with basant's existing subtitle addon.
- **No runtime TMDB calls on the stream path.** All TMDB→IMDb resolution happens at catalog-build time (§7.2). This is what makes the stream timing budget close (§7.1).
- **Stateless handlers + persistent store.** Catalog rows and the TMDB→IMDb map live in a persistent store (§6.3), not in memory — Vercel serverless instances are stateless and short-lived.
- **No configure page in v1.** Behaviour is fixed by this spec (languages, 1080p cap, sorting). The manifest lives at `/manifest.json` directly. A configure page (e.g. language order, 720p-only mode) is a possible v2, only if basant asks.

## 5. Hosting — recommendation: Vercel Hobby (free)

| Option | Verdict | Why |
|---|---|---|
| **Vercel Hobby (free)** | **RECOMMENDED** | basant already has Vercel connected (rokdaa, mybite live there). HTTPS + CORS out of the box. Env vars for the TMDB key. Cron Jobs available on all plans (Hobby: max 100 jobs, once per day — exactly the daily rebuild cadence). `getRouter` mounts as an API route (see note below). |
| Cloudflare Workers (free) | Rejected | Documented risk: Torrentio may block Cloudflare Worker IPs (AIOStreams README: "A Cloudflare Worker may get blocked by Torrentio"). |
| Render free | Rejected | Free instances sleep after 15 min idle; wake takes ~30–60 s — breaks Nuvio's 10 s stream timeout. |
| Railway | Rejected | No free-forever tier (trial credit / paid Hobby after) — fails the free constraint, not a sleep issue. |
| Simular Box (his cloud computer) | Rejected | Not 24/7: the Box sleeps, and the free tier deletes a box asleep 14 days straight. Not a hosting solution. |
| His laptop | Rejected | Not always on; the addon must answer when Nuvio asks, even if the laptop is off. |
| ElfHosted private instance ($9/mo) | Rejected | Paid — violates the free constraint. (Its *public* instances are what we call as sources, not where we host.) |

**Vercel limits that shape the design (Hobby plan):**
- Serverless function max duration **10 s**. Nuvio's stream timeout is also 10 s (basant set it to 10 s). So the stream handler has a hard internal budget of **~7 s**: parallel fan-out with per-source timeout **3.5 s**, plus parse/format. A hard overall deadline returns partial results at ~7 s no matter what — the handler never waits for stragglers.
- Cold starts (~1–3 s) eat into that budget on the first request after idle. With the budget above, worst case is ~1–3 s (cold) + 3.5 s (slowest source) + <0.5 s (parse/format) ≈ 5–7 s — it closes. (v1's arithmetic did not close because it also did a sequential TMDB lookup on the stream path; v2 removes that call entirely.)
- **Residual shared-IP risk (honest note):** Vercel egress IPs are shared, so the same *class* of Torrentio block that rejects Cloudflare Workers is possible on Vercel too. Mitigation is the graceful degradation in §7.1 (Comet + HdHub cover the gap) plus the circuit-breaker (§7.1). It does not change the recommendation — every free host shares egress IPs.
- **Express adapter note:** `getRouter` returns an **Express router**, not a plain `(req, res)` handler. A Vercel API route therefore needs a small Express app (or equivalent adapter) wrapping the router; a bare Vercel function cannot mount it directly.
- **Cron note:** Vercel Cron Jobs are available on Hobby (once per day). Official docs now call Cron Jobs a "legacy feature" migrating to Schedules — the daily rebuild must be built against whichever scheduler is current at implementation time.
- Deploy target: a new Vercel project under basant's connected Vercel account (created at implementation time, with his go-ahead). TMDB key stored as a Vercel env var, never in code or the manifest.

- **Manifest size budget:** the SDK enforces a manifest under 8 KB when stringified (exceeding it throws at build time). A minimal catalog entry `{type, id, name}` is ~70–110 bytes, so 27 entries ≈ 2.0–3.0 KB + base manifest (~0.5–1 KB for id, version, name, description, resources, types, `idPrefixes`, logo URLs) ≈ **2.5–4.0 KB total — verified 2,979 bytes locally for v2.0, comfortable headroom**. (v1's "little headroom" was overstated.) The trim order, if ever needed: drop the `series` half of the narrowest pairs first (Underrated Gems, Sci-Fi & Time Travel series), then single rows by lowest use. **No `extra` fields** (search/genre/skip) on any v2 catalog — adding one requires recounting the manifest.
- **Catalog response shape:** handlers return `{ metas: [...] }` with no `extra` declared (browse-only rows, no search). Each preview carries `id`, `type`, `name`, `poster` (+ `posterShape: "poster"`, `releaseInfo`, `description` where available). Stremio's standard page size is 100; a 20-item single response is under 100, which correctly signals end-of-row — **no `skip` pagination in v2** (single-page rows).
- **Ordering on the Discover page:** catalogs are declared in manifest order, "Trending in India" first. (Nuvio shows installed addons' catalogs in manifest order; the exact board position also depends on Nuvio's own board logic — verify in testing, T1/T2.)

### 6.2 How the rows are computed (TMDB)

All queries run at **catalog-build time** (daily cron, §6.3), never per user request.

**v2.0 rows (18 Nov 2026 — basant's 25-item mega-list, 27 catalogs):** the v1 rows are dropped entirely (New Indian Releases, OTT Releases, Popular Indian, Top Indian, Top This Month, Top This Year, Hindi Movies/Series, Hindi Dubbed). Every row caps at 20 items. Pairs are movie + series; singles are one type only (see §6.1). Detail-heavy rows reuse one detail call per title for the imdb id + all filters (movie: `/movie/{id}?append_to_response=external_ids,release_dates`; series: `/tv/{id}?append_to_response=external_ids`), cached per build run.

- **#1 Trending in India (both):** `/trending/{type}/week`, Indian titles only (original_language in hi/te/ta/ml/kn/bn/mr/gu/pa, else detail origin_country == IN). Up to 5 pages. No top-up row anymore (Popular Indian is dropped) — a thin row stays thin.
- **#2 Trending Worldwide (both):** `/trending/{type}/week`, no filter. Up to 3 pages, cap 20.
- **#3 Fresh Digital / OTT Drops (movie):** discover by `release_date` window (last 45 days), **Indian-only — `with_origin_country: 'IN'` (v2.0.2, basant's call 18 Nov 2026: the global row read as a world row, top titles German; was global in v2.0/v2.0.1)**, vote_average>=6, sort `release_date.desc`; then the detail check: any country's type-4 (Digital) release date inside the window. Final order is the actual digital date desc (from the detail). Up to 3 discover pages (60 detail calls max). **Probe evidence (first rebuild, 45-day window): the row filled to 20/20 — no widening to 90 days needed** (the 45-day Indian digital pool is healthy: The Third Murder, Happy Journey, Daayra, Parivarik ManuRanjan, Jailer 2 on top).
- **#4 Latest Indian Movies — OTT Ready (movie):** discover origin IN, `primary_release_date` last 90 days, sort date desc; same digital detail check as #3 (type 4, any country, in window). Up to 3 pages (60 detail max).
- **#5 Latest Indian Web Series (series):** discover origin IN, `first_air_date` last 90 days, sort date desc, WITH the v1.4 TV-show filter. Up to 5 refill pages.
- **#6 Releasing Next 30 Days (both):** `primary_release_date` / `first_air_date` within the next 30 days, sort **popularity.desc** (hype proxy — no Trakt watchlists in TMDB). Date-asc was considered and rejected: it would put the nearest-dated obscure titles first; popularity inside the window puts the biggest upcoming titles on top (same reasoning as the v1.2 New Releases sort change).
- **#7 Big Announcements 2026–2027 (both):** status Planned / In Production, release within the next 500 days, sort popularity. TMDB discover has NO status filter for movies — the movie side filters by status via detail calls (up to 3 pages, 60 detail max). The series side filters in discover (`with_status=1|2`) and the detail verifies it again. **Substitution, honest:** "Announced" is NOT a TMDB status value (movie: Rumored/Planned/In Production/Post Production/Released/Canceled; TV: Returning Series/Planned/In Production/Ended/Canceled/Pilot) — Planned is TMDB's equivalent of "announced".
- **#8 Newly Announced Web Series (series):** discover `with_status=1|2` (Planned/In Production), `first_air_date` within next 365 days, sort popularity. Detail verifies status + TV filter. Up to 3 pages.
- **#9 New Season Returning Soon (series):** discover `with_status=0` (Returning Series) + `air_date` window (an episode airing in the next 45 days); detail verifies status AND `next_episode_to_air.air_date` inside the window; the row is then sorted by that air date asc. **Approach verified workable** (18 Nov 2026, TMDB API docs): `with_status` and `air_date.gte/lte` are real `/discover/tv` parameters and `next_episode_to_air` is a real `/tv/{id}` field. **Honest caveat:** a Returning Series between seasons has `next_episode_to_air=null` when TMDB knows no date yet — those shows cannot appear here (no date to sort by), so the row only holds shows with a known next date. Up to 3 pages (60 detail max).
- **#10 Now in Theatres (movie):** `/movie/now_playing`, region IN, vote_count>=10 (client-side filter; v2.0.1 — was 1000, which gave 0 titles: current Indian releases have very few TMDB votes, Ramayana 57, Jailer 2 40; probed 18 Nov 2026: >=1000: 0 pass, >=100: 5, >=50: 7, >=10: 13), popularity order. Up to 5 pages (was 3) — the row lands at ~13, honest, not padded.
- **#11 South Indian Blockbusters (movie):** ONE combined row (not per-language): `with_original_language=te|ta|ml`, vote_average>=7, last 2 years, sort popularity.
- **#12 Indian Dark Crime & Thrillers (series):** origin IN, genres Crime/Mystery, vote_average>=7.2, sort vote_average desc, WITH the v1.4 TV filter. (TV has no Thriller genre — see #20.)
- **#13 Underrated Indian Gems (both):** origin IN, vote_average>=7.8, vote_count 2000–25000 (the "underrated" band: loved, but not widely voted), sort vote_average desc.
- **#19 Mind-Bending Sci-Fi & Time Travel (both):** genre Sci-Fi (movie 878 / TV 10765 Sci-Fi & Fantasy), keywords time travel / simulation / space / dystopia, vote_average>=7.3, sort popularity desc (v2.0.1 — was vote_average desc, which surfaced unknown high-rated titles like CYBEROW and Hell PHYRE; popularity order leads with Project Hail Mary, Interstellar, The Matrix, Dune, Rick and Morty, Doctor Who — probed 18 Nov 2026). Global, not India-only. **Keyword ids are resolved AT BUILD TIME via `/search/keyword`** (exact case-insensitive name match); no ids are hardcoded. A term the endpoint cannot resolve is dropped and logged (`stats.keywords.dropped`); if all drop, the row is genre-only (logged, not faked).
- **#20 High-Tension Psychological Thrillers (both):** genres Thriller/Mystery, vote_average>=7.5, vote_count>=20000 (movie, unchanged) / >=2000 (series; v2.0.1 — was 20000 for both, series pool was 1 title; probed 18 Nov 2026: series vc>=10000: 9, >=5000: 25, >=2000: 83, of which 58 survive the v1.4 TV filter — Breaking Bad, Dexter, Sherlock, True Detective, Peaky Blinders), sort popularity. **Series side substitution:** TMDB has NO Thriller genre for TV — the series side uses Mystery + Crime.
- **#21 Adrenaline Action, Heist & Revenge (movie):** genres Action/Crime, vote_average>=7, vote_count>=25000, sort popularity.
- **#22 1-Season Binge Mini-Series (series):** TMDB type Miniseries preferred (`with_type=2`), else status Ended + `number_of_seasons<=1`, vote_average>=7.8, vote_count>=1000 (v2.0.1 — was 10000, pass-1 pool was 1 title; probed 18 Nov 2026: vc>=5000: 3, >=2000: 7, >=1000: 26; pass-2 pool 299), sort vote_average desc, WITH the v1.4 TV filter. Two passes: `with_type=2` first (up to 5 pages), then the Ended fallback only if the row is still short.
- **#23 4K IMAX Visual Spectacles (movie):** genres Sci-Fi/Adventure/Fantasy, vote_average>=7.5, after 2015, sort popularity. **HONEST LIMIT: TMDB carries no IMAX/4K flag — there is no way to verify a title is actually IMAX or 4K from TMDB data.** This row is a genre + rating proxy for visually spectacular titles; the NAME stays as basant wants it.
- **#24 Top Action & Dark Anime (series):** genre Animation, origin JP, vote_average>=8, vote_count>=1000 (v2.0.1 — was 10000, pool was 0; probed 18 Nov 2026: vc>=5000: 10, >=2000: 27, >=1000: 70; episode check on the first 60: 45 under the 100-ep cap — Frieren, Fullmetal Alchemist: Brotherhood, Attack on Titan, Death Note), sort vote_average desc (v2.0.1 — was popularity desc, whose order is full of long serials the cap kills first), up to 20 pages (was 10), WITH the v1.4 TV filter. Honest note: the 100-episode cap excludes long-running anime (One Piece etc.) — the filter working as designed.
- **#25 All-Time Classics (movie):** substitute for the exact IMDb Top 250 (not available via TMDB) — TMDB `/movie/top_rated`, plus a vote_count>=10000 floor (v2.0.1: top_rated alone lets unreleased/few-vote titles top the list — the wrong top 6 had 338–2400 votes; probed 18 Nov 2026: vc>=10000 top 5 = Shawshank, Godfather, 12 Angry Men, Godfather II, Schindler's List; 30 pass in 3 pages; released-only alone does NOT fix it). Up to 3 pages.

**Substitutions (all accepted by basant, all for the same reason — the source does not exist in TMDB):** IMDb ratings → TMDB `vote_average`/`vote_count`; IMDb Top 250 → TMDB `/movie/top_rated`; Trakt watchlists → `popularity` (hype proxy); "Announced" status → Planned + In Production; IMAX/4K verification → genre + rating proxy (unverifiable, stated plainly); Thriller TV genre → Mystery + Crime; Sci-Fi keywords resolved at build time via `/search/keyword` (no hardcoded ids; unresolvable terms dropped + logged); #6 sort popularity.desc, not date-asc (date-asc would surface obscure nearest-dated titles first); #9 approach verified workable (`with_status` + `air_date` window + `next_episode_to_air` — but shows with a null next date cannot appear); #22 two-pass (`with_type=2` first, then Ended + <=1 season fallback); #24's 100-episode cap excludes long-running anime (One Piece etc.) by design.

**Dropped in v2.0:** New Indian Releases, OTT Releases, Popular Indian, Top Indian, Top This Month, Top This Year, Hindi Movies/Series, Hindi Dubbed (all 20 v1.4 catalogs). **Not in this build:** items #14–18 of basant's 25-item list are OTT shelves — a separate Nuvio Catalog Addon step for basant, not part of this build.

**Series rows — TV-show filter (v1.4, 18 Nov 2026):** basant reported "series ke andar TV show aa rahe hain" — Popular Indian - Series was showing C.I.D., Kyunki Saas Bhi Kabhi Bahu Thi, The Kapil Sharma Show (broadcast TV), not web series. **Rule: a series row holds web series only; broadcast TV shows are excluded at build time, in ALL 13 series rows** (v2.0). Movie rows are untouched. Three filter layers, applied on the TMDB `/tv/{id}` detail (one call with `append_to_response=external_ids` returns the imdb id AND the filter fields together, replacing the separate `/external_ids` call for series; the detail is cached per build run and reused by the Trending check and the status checks in #7/#8/#9): **(1) type** in {Talk Show, Reality, News, Video} → exclude; keep Scripted, Miniseries, Documentary. **(2) number_of_episodes > 100** → exclude. **(3) broadcast-network blocklist** (exact TMDB network names, spaces stripped + lowercased): Star Plus, Sony Entertainment Television, Sony SAB, SAB TV, Colors, Colors TV, Zee TV, Star Bharat, &TV, DD National, Life OK, Star One, Imagine TV, Sahara One, Sony Pal, Star Utsav, Zee Anmol, Dangal TV, Dangal, Zindagi + regional GECs (Sun TV, Star Vijay, Vijay TV, Zee Tamil, Colors Tamil, Star Maa, Zee Telugu, Asianet, Star Jalsha, Zee Bangla, Colors Kannada, Star Suvarna, Zee Marathi, Colors Marathi, Star Pravah, Sony Marathi, Zee Kannada, ETV, ETV Telugu, Gemini TV, Sony Vizha, Jaya TV, Kalaignar TV, Raj TV, Vendhar TV, Polimer TV, Vasanth TV). **Name trap found in live verification:** TMDB stores the Colors network as "Colors", NOT "Colors TV" — Comedy Nights Bachao (64 eps, Colors) and 24: India (48 eps, Colors) slipped past the first list, so 'colors' is listed on its own; same for new Tamil GEC Sony Vizha (Tamil Idol + Celebrity MasterChef Tamil are reality shows on Sony Vizha, but TMDB types them Scripted — only the network name kills them). OTT networks are deliberately NOT blocked (Netflix, Prime Video, Sony LIV, JioHotstar, ZEE5, ULLU, MX Player…) — no content/genre filtering beyond this TV-show rule. **Probe evidence (TMDB website, 18 Nov 2026):** TV shows — C.I.D. 1,651 eps / Scripted / Sony Entertainment Television; Kyunki Saas Bhi Kabhi Bahu Thi 2,287 / Scripted / Star Plus; The Kapil Sharma Show 474 / **Talk Show** / Sony Entertainment Television; Taarak Mehta Ka Ooltah Chashmah 4,870 / Scripted / Sony SAB. Web series (kept) — Sacred Games 16, Mirzapur 29, Scam 1992 10 (Miniseries), Panchayat 40, Charmsukh 56 (ULLU). **Why three layers:** type alone does NOT kill the soaps (TMDB marks them "Scripted", its default type — only the Talk Show dies by type); the cap (100) sits between the biggest real web series probed (56, Charmsukh) and the smallest TV show probed (474, Kapil); the network layer is needed because short/finite broadcast series slip past both — Yudh (Sony TV, 20 eps) and 24 (Colors, 24 eps) are Scripted + under the cap, so only the network kills them. **Refill:** freed slots are backfilled from later discover pages (v2.0: vote-filtered rows scan up to 10 pages, standard series rows up to 5, announcement/returning rows up to 3) so rows stay full; a row stays short only if the pool is genuinely exhausted. Excluded titles are counted + named in the rebuild response (`excludedTvShow`). **Known limit, honest:** Global Trending series can still show a short Western broadcast show (the cap kills long runners like The Simpsons/Grey's Anatomy, but the network list is Indian-only by design).

**TMDB call budget (v2.0, recomputed):** discover/list calls ~130/run worst case (trending 8 + 6 pages, digital/OTT/announcements ~9 + 9, the rest 2–3 pages each, plus 4 keyword searches); detail/external_ids calls: first run ~700–1,500 (the persisted id map starts empty and every series candidate needs a detail call; worst case if every series row scans its full refill depth), steady state ~500–900/day (the id map covers repeat movie titles; series details re-fetch daily for titles still in the windows). Concurrency 10, 429 backoff unchanged. **Estimated rebuild time: first run ~45–75 s, steady state ~30–60 s** (v1.4 measured 31 s with ~700 calls) — inside the 300 s cron limit with wide margin. The rebuild is parallelised (batched concurrency, 10 in flight).

**TMDB key, limits, attribution:**
- Free key for non-commercial use; basant creates it at themoviedb.org → Settings → API (v3 key or v4 read token). Rate limit: the old hard 40-requests/10-seconds limit was disabled Dec 16, 2019; the current upper bound sits somewhere around ~40 req/s and is not guaranteed — **respect HTTP 429 with backoff**. Our ~700–1,500 calls per daily rebuild cannot plausibly hit it.
- **Attribution is a design requirement, not a footnote:** the addon must display the TMDB logo and the notice *"This product uses the TMDB API but is not endorsed or certified by TMDB"* (manifest description / about text). The addon is non-commercial, so no paid TMDB licence applies.

### 6.3 Caching & refresh (daily updates) — rewritten: persistent store, not in-memory

v1's "in-memory + daily cron rebuild" **cannot work on Vercel serverless**: functions are stateless, short-lived, scale-to-zero instances with no shared in-memory store. A cron invocation warms exactly one instance; any other (or cold) instance sees an empty cache, and there would be no durable "yesterday's rows" anywhere.

**v2 design:**
- **Catalog rows and the TMDB→IMDb id map live in a persistent store: Vercel Blob (one JSON file per catalog + one map file).** Verify the free-tier allowance at implementation time; fallback if Blob is unavailable is Vercel KV. If neither is available, the fallback is lazy per-request rebuild with CDN caching (documented here, with the caveat that first-loads may be slow).
- **Daily cron rebuild** (Vercel Cron, once per day on Hobby): parallelised TMDB discover + `external_ids` only for items not already in the persisted map + detail post-filters (digital-release, status, miniseries checks) for new candidates only; writes new row JSON to Blob; **on failure it writes nothing — yesterday's files keep serving**. The rebuild is batched so it fits the 300 s cron budget.
- **Catalog handler:** reads the row JSON from Blob (fast, <100 ms expected), returns `{ metas, cacheMaxAge: 86400, staleError: 86400 }` — the SDK's handler return fields, which set `Cache-Control: max-age=86400` plus a stale window so yesterday's rows keep serving even if a rebuild fails. The handler never calls TMDB.
- **Posters:** TMDB image CDN (`https://image.tmdb.org/t/p/{size}/{path}`), `w342` for row posters (small, fast on hotspot data), `w500` for posters, `w780`/`w1280` for backdrops (`w500` is a poster size only, not a backdrop size). Poster URLs are plain CDN links — no key needed to fetch them.

### 6.4 Meta (detail pages) — resolved by Cinemeta via `tt…` ids

**v1's plan was wrong and is replaced.** Live probes prove Cinemeta does **not** resolve `tmdb:` ids: `https://v3-cinemeta.strem.io/meta/movie/tmdb:27205.json` → HTTP 404, while the same title by IMDb id (`tt1375666`) → 200 with full meta. Cinemeta's manifest declares `"idPrefixes": ["tt"]` only. With `tmdb:` catalog ids and no meta handler, clicking any catalog item would show no detail page, and for series there would be no `videos[]` episode list at all — no episode could ever be selected and no stream request issued.

**v2 design (Option A — `tt…` catalog ids):**
- Catalog items carry **`tt…` IMDb ids**, resolved from TMDB at catalog-build time via `/movie/{id}/external_ids` (or `/tv/{id}/external_ids`), using the persisted map (§6.3) so only new items cost a call.
- **Titles with no `imdb_id`:** excluded from catalog rows. The row backfills from the next-newest title in that language so rows stay full; the build logs how many were excluded. Trade-off (honest): a small number of very new/regional titles without IMDb entries will not appear in rows — they remain findable via search and other addons. (TMDB→IMDb coverage for Indian theatrical releases is high; the exclusion rate is expected to be low and is visible in build logs.)
- Detail pages (title, description, cast, background, episode lists) are then resolved by **Cinemeta**, the established pattern — no meta handler in v1.
- **Manifest `idPrefixes` (now specified — v1 omitted it entirely):** top-level `types: ["movie", "series"]`; the stream resource declares `idPrefixes: ["tt"]`. With `tt` in the prefixes, the addon is queried for **all** Cinemeta titles the user opens, not just its own rows — that is intended (§8 step 4: Bharat Streams is an additional stream source for every title). `idPrefixes` does not apply to `catalog`, so the catalog rows are unaffected.
- **Full manifest field list (v1 omitted several):** `id` (`com.bharatstreams`), `version` (semver, e.g. `1.0.0`), `name` ("Bharat Streams"), `description` (including the TMDB attribution notice), `resources: ["catalog", "stream"]`, `types: ["movie", "series"]`, `idPrefixes` on the stream resource, `catalogs` (24 entries, §6.1), `behaviorHints: { p2p: true }` (the SDK's flag for addons containing BitTorrent content, which may reveal the user's IP — used to show the user an adequate warning).

### 6.5 Posters — RPDB evaluation (softened)

- **Primary poster source: TMDB CDN (w342/w500).** Free, high quality, no key needed. This alone satisfies "good high-quality posters".
- **RPDB (RatingPosterDB) as an optional enhancement:** RPDB bakes IMDb/RT ratings onto the poster image. The key `t0-free-rpdb` is a **community-published free-tier key** seen in Nuvio Wiki and community guides — but its official status is disputed: ElfHosted's RPDB docs FAQ states RPDB issues API keys only to subscribers of a paid Patreon tier ("Is there a free RPDB API key? No."). Soften the v1 claim accordingly: the key is community-shared, not confirmed as RPDB's own public key, and its rate limits are undocumented. The image URL format is confirmed by AIOMetadata's own code: `https://api.ratingposterdb.com/{rpdb_key}/imdb/poster-default/{imdb_id}.jpg?fallback=true` (since catalog ids are now `tt…`, the `imdb` path applies).

## 7. Streams

### 7.1 Fan-out

On `GET /stream/{type}/{id}.json` (ids are `tt…` only, §7.2):
1. Fire **parallel** `GET {base}/stream/{type}/{id}.json` to the three sources with a **per-source timeout of 3.5 s** and a **hard overall deadline of ~7 s** — at the deadline, return the partial results collected so far regardless of pending sources. (v1 said "never wait for stragglers" while using `allSettled` with a 5 s timeout, which *does* wait for the slowest source on every request. v2's deadline is the real mechanism.)
2. **Per-source validation (v1 named failure modes but specified none of them):** HTTP status must be 200 with a JSON content-type (a 403/429/500 returning an HTML error page must be caught here, not at JSON parse); `try/catch` the JSON parse; validate the shape is `{streams: Array}`; validate each stream has `infoHash` or `url` (a stream with neither is dropped); **cap input at ~150 streams per source before parsing** (a live Torrentio response for one title ran to 1,132 lines — parsing everything from 3 sources inside the budget is unaddressed without a cap).
3. A source that errors, times out, or returns malformed JSON is **skipped** — never fail the whole response because one source failed. But it is **not skipped silently**: log the per-source outcome server-side (source, status, stream count, latency) so a permanently dead source is detectable. On total failure of all sources, return `{streams: []}` and log it distinctly from "no streams exist".
4. **Circuit-breaker:** if a source fails 3 consecutive times (or returns 403/429), back off from calling it for N minutes (per-instance flag + log). Without this, a blocked source burns 3.5 s on every request.
5. **Rate limits:** ElfHosted's public instances are rate-limited (their docs describe an allowance that refills over time). Respect `Retry-After` / 429 with backoff; never hammer a source that rate-limited us.
6. Parse → filter → dedupe → sort → format (§7.3–§7.6) → return `{ streams: [...] }` (cap 40, applied **after** sorting).

### 7.2 ID handling — `tt…` only, resolved at build time

- Stream requests arrive with `tt…` ids only: `tt1234567` (movie), `tt1234567:1:2` (series S1:E2). This follows from §6.4 (catalog items are `tt…`; `idPrefixes: ["tt"]`).
- **There is no runtime TMDB lookup on the stream path.** All TMDB→IMDb resolution happens at catalog-build time (§6.3–§6.4). This is what makes the §7.1 timing budget close.
- Titles with no `imdb_id` never reach the stream handler as catalog items (excluded at build, §6.4). If a `tmdb:` id ever arrives anyway (defensive case), the handler returns `{streams: []}` for it and logs it — it does not attempt a runtime resolution.
- Note (dropped source, recorded for accuracy): MediaFusion's live manifest lists `"idPrefixes": ["tt", "tmdb:", "tvdb:", "mal:", "mf", "dl"]` — it *can* accept `tmdb:` ids directly. That capability is not used in v1 because the other sources cannot, and the design keeps one id format throughout.

### 7.3 Parsing — per-source, line-anchored (v1's token table was wrong)

Stremio stream objects carry **no structured language/resolution/seeders fields**. Everything is parsed from the `name`/`title`/`description` strings — **and from `behaviorHints.filename`, which Torrentio supplies as a clean release filename and is the best parse input** (v1 never mentioned it).

**The critical correction (live evidence):** Torrentio marks language as a **flag-emoji line**, not word tokens. A live Torrentio response for `tt0111161` shows: `"title": "... 👤 113 💾 78.61 GB ⚙️ Rutracker\n🇬🇧 / 🇷🇺"`. v1's token table (`Hindi`, `HIN`, `Dual Audio`…) would have parsed most Torrentio streams as `Unknown`, sinking them to rank 5 and defeating Hindi-first sorting. The parser must therefore be **per-source and line-anchored, not concatenated-token**:

| Source | Language location | Parse rule |
|---|---|---|
| Torrentio | Last line of the title/description: flag emojis (`🇬🇧 / 🇷🇺`) | Emoji→language map (§7.3 table). Also parse `behaviorHints.filename` for resolution/codec/tags. |
| Comet | Line after the `🔎` site marker | Same emoji map; language line follows the site line. |
| MediaFusion | — | **Dropped from v1 (Phase 2 pre-test: 0 streams).** HdHub parsing lives in the implementation (`lib/parse.js`). |

**Emoji→language map (core):** 🇮🇳 Hindi, 🇬🇧 English. **Drop set** (for §7.4): Tamil, Telugu, Malayalam, Kannada, Bengali, Marathi, Gujarati, Punjabi, Korean, Russian, Japanese, Chinese, Spanish, French, German, Thai, Vietnamese + their ISO codes (`ta/te/ml/kn/bn/mr/gu/pa/ko/ru/ja/zh/es/fr/de/th/vi`) and flag emojis where they exist. (Tamil has no distinct flag emoji — Tamil-only streams are detected by word/code tokens, not flags.)

| Field | How to parse | If unparseable |
|---|---|---|
| **Resolution** | Regex on filename/title: `2160p`/`4K`/`UHD`/`2160` → 2160; `1440p`/`2K` → 1440; `1080p` → 1080; `1080i` → 1080i (ranked below 1080p); `720p` → 720; `480p`/`SD` → 480. Precedence: if a title contains two resolutions, the **highest wins for the drop decision** (a title mentioning both 2160p and 1080p is treated as 2160p and dropped). Bare `HD` alone is ambiguous → unknown. | `unknown` — ranked **below 480p** (last). Rationale: an unparseable stream might be 4K; the 1080p cap is a safety rule, so unknown resolution must never auto-play ahead of a known ≤1080p stream. |
| **Language set** | Emoji map + word/code tokens per source line (above). A stream's language is a **set** (e.g. {Hindi, English} = Dual), not a single label. | `unknown` (see §7.4 / D1). |
| **Audio tags** | `Atmos`, `TrueHD`, `DTS-HD MA`, `DTS`, `DD+`, `DD`, `AAC`, `FLAC`, `Opus` — for the description line. | Omit from the line. |
| **Visual tags / encode** | `HDR10+`, `HDR10`, `DV`/`Dolby Vision`, `HDR`, `HEVC`/`x265`, `AVC`/`x264`, `BluRay`/`Blu-ray`, `WEB-DL`/`WEBRip`, `10bit` — for the description line. | Omit. |
| **Seeders** | **Only** `👤 (\d+)` — the one evidenced pattern (live Torrentio: `👤 113`). v1's `Seeders:`, `S:`, `[N]` patterns are **deleted**: they appear in no real sample and are dangerous false positives (`[12]` could be a year/episode/file index; `S:12` a season marker). | `null`. Debrid/cached results carry no seeders at all, so `null` seeders are **common, not exceptional** — they sort after any stream with a known count at the same tier. |
| **Size** | `💾 X GB` / `GB`/`MB` token — display only. | Omit. |

- **Parser built against real samples:** the parser must be written against captured real responses from all three sources (implementation task: one real response per source for a Hindi movie and an English movie). A stream that fails to parse for resolution is kept as `unknown` resolution, never dropped for parse failure alone — only the §7.4 filters drop streams.
- **Dedupe (fixed — v1's key broke on real data):** live Torrentio data shows streams **with no `fileIdx` field at all**, and HTTP/debrid streams carry a `url` and no `infoHash`. v1's key (`infoHash + fileIdx`) collides across different files of one torrent, and all url-only streams would share one key. **v2 key:** `infoHash + (fileIdx ?? 0)` when `infoHash` exists; else `url`; else skip dedupe. Cross-source title dedupe: normalisation is now defined — lowercase, strip punctuation/year/resolution/language/codec tokens — and dedupe runs **after sorting, keeping the best-ranked copy** (v1's "keep the first" was nondeterministic parallel-arrival order). The "note the source in the retained copy's metadata" line is deleted: Stremio stream objects have no such field; the source is kept server-side for logging only.

### 7.4 Filtering (spec order, now implementable)

1. **Drop 2160p / 4K / UHD / 1440p / 2K** — always, no exceptions. (1440p is above the 1080p cap, so it is dropped with 2160p — v2 corrects the reviewer's rank-between-1080-and-720 suggestion, which conflicts with the spec's hard cap.)
2. **Drop CAM / TS / HDCAM** — theatre recordings, common for *new* Indian releases (the catalog's core). They carry no resolution token and would otherwise parse as Unknown resolution and could auto-play. Excluded entirely.
3. **Language filter (set-based):** let L = the stream's parsed language set.
   - If **Hindi ∈ L** → keep (Hindi rank, §7.5).
   - Else if **English ∈ L** and L contains no drop-language → keep (English rank).
   - Else if L ⊆ {Dual, Multi, Original} with no Hindi/English and no drop-language → keep (Original/Multi rank).
   - Else if L contains **only** drop-languages (e.g. Tamil-only, Telugu-only, Korean) → **drop**.
   - Else (L empty) → **Unknown** → decision D1.
4. **Liveness filter (new — v1 had none):** a Hindi 1080p torrent with 0 seeders previously sorted first in its tier (seeders only order *within* a tier) and would auto-play into a stall. v2: **drop 0-seeder streams when any seeded alternative exists**; if no seeded alternative exists at all, keep the best 0-seeder stream ranked last. The auto-play pick must have seeders ≥ 1 (AIOStreams' own guidance — minimum seeders 1 — supports this).
5. **Unknown language (D1):** default = **include Unknown at the LOWEST priority** (after all tagged streams), because with auto-play-first-source it only plays when nothing tagged exists — in which case something is better than nothing. If basant prefers the strict spec reading, one flag excludes Unknown entirely. **Consequence stated plainly:** with D1=include, when no tagged stream exists, auto-play can play a wrong-language file — that is the real cost. Tests T6/T7 are written conditional on D1 (§9).
6. **Result cap:** 40 streams max, applied **after** sorting.

### 7.5 Sorting (spec order — language → resolution → seeders; set-based)

v1 ranked "Original" below English and "Multi" below English without checking which languages they contain — for Indian titles "Original" is usually Hindi, so an original-Hindi stream lost to an English dub, contradicting Hindi-first. v2 ranks by **whether Hindi is present in the language set**:

1. **Language rank:** Hindi present in set (Hindi-only, Dual-with-Hindi, Multi-with-Hindi) = **0**; English-only = **1**; Original (no qualifier — see note) = **2**; Multi without Hindi = **3**; Unknown = **4**.
   - Note on "Original": Torrentio often qualifies it (`Original (Eng)` = original-English). Where the qualifier names a language, rank by that language's rules above. Bare "Original" with no qualifier ranks 2 — for a Hindi title this may lose to an English dub, a known edge case, accepted because the qualifier usually disambiguates.
   - Dual/Multi are **sets, not labels**: a Tamil+Telugu Dual contains only drop-languages and is dropped by §7.4 step 3; a Hindi+English Dual is rank 0.
2. **Resolution:** 1080p, then 1080i, then 720p, then 480p, then Unknown (last, §7.3).
3. **Seeders:** higher first; `null` (unknown) after any known count at the same tier.
4. **Tie-break:** encode/quality tags first (BluRay > WEB-DL > WEBRip > HDTV), then larger size. (v1's size-only tie-break could promote a bloated REMUX over a lean encode.)

**Deliberate deviation, acknowledged:** the SDK's `defineStreamHandler` guidance says streams "should be ordered from highest to lowest quality" — our language-first order means a Hindi 720p stream outranks an English 1080p stream. That is spec-driven (first stream = Hindi auto-play pick), not a protocol violation (Stremio does not enforce ordering). Recorded here so a later reviewer does not "fix" it back to quality-first.

**The first stream after this sort is the auto-play pick.** Hindi + 1080p + seeded wins, so "Auto-play first source" plays the right file with one click (subject to the scope condition in §8 / D8).

### 7.6 Formatting (minimalist, approved style)

The addon returns each stream already formatted — Nuvio displays what we return:

- **`name`** = the stream title only (the original torrent/release title, cleaned of excess tags). This is the line Nuvio shows first.
  - **Deliberate deviation, acknowledged:** the SDK's convention is that `name` is "usually used for stream quality" (e.g. "1080p", "4K HDR") and `description` carries the details. Our minimalist format puts the release title in `name` and the quality/tags in `description` — the same shape as basant's approved AIOStreams formatter. It is not a protocol violation (`name` is a free optional string), but verify in Nuvio testing (T6/T7) that long release titles display acceptably and are not truncated in a way that hides the quality line. Alternative, if truncation is a problem: `name` = quality label, release title as the first line of `description`.
- **`description`** = two lines, exactly the approved minimalist style:
  - Line 1: `1080p | HDR10 HEVC` (resolution | visualTags + encode)
  - Line 2: `🔊 DD+ 🇮🇳🇬🇧` (audioTags + language flags — 🇮🇳 for Hindi, 🇬🇧 for English; Dual Audio shows both flags)
  - Size appended to line 1 if known: `1080p | HDR10 HEVC 💾 2.5 GB` — display only, never affects sort.
- **`behaviorHints`:** set `bingeGroup` to a stable group key (e.g. `bharat-streams:1080p:hindi`) so Nuvio's "Auto-Play Next Episode" + "Prefer/Reuse Binge Group" picks the same profile for the next episode.
- **`notWebReady` — conditional rule (v1's blanket rule was wrong):** for `infoHash` (torrent) streams, do **not** set `notWebReady`. For `url` streams, set `behaviorHints.notWebReady: true` when the URL is non-HTTPS or non-MP4 (per the SDK: it "needs to be set to `true` if the URL does not support https or is not an MP4 file").
- **Preserve source hints on reformat:** when rewriting `name`/`description`, pass through / preserve the source's `behaviorHints.filename` (highly recommended by the SDK when using `stream.url`), `videoHash`, and `videoSize` where present — the rewrite must not silently drop them, or subtitle matching breaks.
- **What we do NOT put in the output:** no provider branding wars (no "🔥 BEST" labels), no debrid mentions, no ads, no "click here" text. The list stays clean.

### 7.7 What a stream is (playback path — no change for basant)

- The addon returns torrent `infoHash` + `fileIdx` (or an HTTP URL for the few HTTP sources). **Playback itself is unchanged:** Nuvio's built-in torrent engine on his laptop fetches the file — exactly as Torrentio works today. His IP is visible to the torrent swarm during playback, same as today; the addon adds no new exposure (the addon's server only talks to the source addons' JSON endpoints, never to the swarm). The manifest declares `behaviorHints: { p2p: true }` (§6.4) so Nuvio can warn the user appropriately.
- No downloading, no watch history, no accounts, no tracking in the addon.

With AIOStreams and 8 other addons installed, another addon's stream can win the race. So deterministic one-click play requires a Nuvio change (decision D8):
   - **Option D8a (recommended for the guarantee):** Settings → Player → Stream Selection → Auto-play Source Scope / Allowed Addons → restrict auto-play to **Bharat Streams**. Then the first stream is always ours (Hindi, 1080p).
   - **Option D8b (leave as-is):** keep scope "All sources" / Allowed Addons "All installed addons". Then the one-click claim downgrades to "first *within Bharat Streams' list*" and auto-play may pick another addon's stream for some titles.
   - **Verify in testing (T8):** what Nuvio does when the restricted set returns no streams (expected: the manual list appears). If that fallback is bad, D8b is the safer default.
   - His already-set values stay: Auto Stream Selection → "Auto-play first source", timeout 10 s, Reuse Last Link ON.

## 10. Trade-offs (deliberate choices)

1. **`tt…` catalog ids vs `tmdb:` ids:** `tt…` (chosen) uses the proven Cinemeta path and needs no runtime resolution — but titles without an IMDb id are excluded from rows. `tmdb:` ids would keep every title but require a v1 meta handler with series `videos[]` and a runtime resolver.
2. **Own TMDB catalogs vs AIOMetadata:** own catalogs (chosen) give the exact "New Indian Releases, Hindi-first" row; AIOMetadata gives per-language discover rows but no grouped row, plus a shared-service dependency. Cost: we need basant's free TMDB key and we own the catalog logic.
3. **Persistent store (Blob/KV) vs lazy rebuild:** persistent store (chosen) makes "yesterday's rows on failure" real. Cost: a storage dependency whose free allowance must verify at implementation.
4. **Server-side aggregation vs letting Nuvio call sources directly:** aggregation (chosen) is the only way to enforce one merged, filtered, sorted list with "first stream = right stream". Cost: our server is a single point of failure and adds ~1–3 s; mitigated by per-source timeouts, the 7 s deadline, and graceful degradation.
5. **1080p cap vs quality:** 1080p max (chosen, per spec) saves hotspot data and plays smooth on the i3 laptop. Cost: no 4K (and no 1440p) even if his data/Wi-Fi later allows it — a deliberate, reversible choice (filter flags).
6. **Include Unknown-language streams last vs strict spec:** include-last (recommended, D1) keeps untagged Hindi releases; strict would lose them. Cost: a rare wrong-language auto-play when nothing tagged exists.
7. **Unknown resolution ranked last vs ranked by guess:** last (chosen) is the safety rule — an unparseable stream might be 4K, so it must never auto-play ahead of a known ≤1080p stream. Cost: a legit 1080p stream with an odd title ranks last.
8. **No configure page in v1:** fixed behaviour keeps v1 small and shippable. Cost: any preference change (e.g. 720p-only mode) needs a code change, not a toggle.
9. **Cinemeta for meta vs own meta handler:** Cinemeta (chosen, via `tt…` ids) is zero extra code and the established pattern. Cost: detail pages depend on Cinemeta resolving every catalog id (verified for `tt…` by live probe).
10. **Vercel Hobby vs always-on server:** Vercel (chosen) is free and fits; cold starts + 10 s limit + shared egress IPs are the price. An always-on server would cost money or live on hardware that sleeps.
11. **Three sources vs four:** StremThru dropped from v1 (unproven bare endpoint, config required). Cost: one fewer source of streams until it is verified.
